# Scratch Spaces

A Scratch Space is a persistent, disposable place for work on one Node. Choose an existing space when starting a conversation, or leave the choice at **New for this conversation**. A conversation keeps its choice for its lifetime. The creator and members can use and manage the space. An Agent can use it only while the person who started its conversation may do so. A delegated Run uses a space on the receiving Node.

New spaces default to 100 GiB capacity, 14 days of idle expiry, four CPU cores, 16 GiB memory, and daily budgets of 100 GiB each for sent and received traffic. An idle expiry may instead be disabled. The allowed hosts default to common package, source, and container registries, narrowed by the Tenant's allowlist. Adding a host to a space cannot broaden that allowlist. Data sent to allowed hosts is outside Aidash's data protection guarantees.

A space may choose an execution image and External services. Without an image it uses the Tenant's default. Image references are pinned by digest and must be approved for the Tenant in the Deployment configuration. Tenant-managed image approval is part of the image lifecycle work. External services are shared with every member of the space; their credentials remain at the Egress gateway. Docker is available only when the Deployment operator permits it for the Offering or Tenant, and then only when the space enables it. Docker-enabled Pods must run on nodes dedicated to that Tenant. Clear or delete marks the space unavailable and records the intent to reclaim its disposable contents. The Execution Pod runtime must consume that intent to reclaim the contents. Idle expiry denies access after the configured period; runtime cleanup and Node purge wiring are supplied by their respective lifecycle work. Tenant purge is enforced by the database ownership relationships.

The Tenant policy action `scratch.create` controls space creation and is allowed to Tenant users by default. Deployment Administrators have no Tenant authority to read spaces.

## Operator configuration

The `[deployment]` settings `scratch_capacity_bytes`, `scratch_cpu_millis`, and `scratch_memory_bytes` set ceilings. Capacity defaults to a ceiling of 1 TiB; the CPU and memory defaults are 4,000 millicores and 16 GiB. `scratch_docker_allowed` enables Docker for the Offering, and `scratch_docker_tenants` lists additional Tenants for which Docker may be enabled. `scratch_all_hosts_allowed` controls whether the Offering permits choosing all hosts. `scratch_tenant_hosts` maps Tenant names to their permitted host lists; a one-element `['*']` list represents all hosts. Without a Tenant entry the public-registry defaults apply. `scratch_tenant_images` maps Tenant names to approved image references.

## HTTP API

`POST /api/conversations` accepts optional `scratch_space_id`; omission creates a new space on the conversation's Node in the same admission transaction. `GET` and `POST /api/scratch-spaces` list and create spaces. Creation accepts a Node, name, and optional settings; when settings are omitted the defaults are narrowed to the Tenant allowlist. `GET` and `DELETE /api/scratch-spaces/{id}` read and delete one. Settings are updated with `PATCH /api/scratch-spaces/{id}/settings`. Members are added with `POST /api/scratch-spaces/{id}/members` and removed with `POST /api/scratch-spaces/{id}/members/remove`; both accept a subject. `POST /api/scratch-spaces/{id}/clear` clears it. `GET /api/scratch-spaces/limits?node=...` returns effective ceilings and the Tenant allowlist for the Node. Each operation requires Tenant authority and applies the space's membership and Node checks.
