# Scratch Spaces

A Scratch Space is a persistent, disposable place for work on one Node. Choose an existing space when creating a Workspace or starting a conversation, or create a dedicated space. The Workspace keeps its choice for its lifetime, and its conversation names the space for people who may use it; anyone else, and anyone looking at a deleted space, sees only that it is unavailable. The creator and members can use and manage the space. An Agent can use it only while the Workspace creator may do so. A delegated Run uses a space on the receiving Node. That space belongs to the Peer Mapping's credential subject, which is a service or agent subject rather than a person.

New spaces default to 100 GiB capacity, 14 days of idle expiry, four CPU cores, 16 GiB memory, and daily budgets of 100 GiB each for sent and received traffic. Idle expiry can be set from 1 to 365 days, or disabled. The allowed hosts default to common package, source, and container registries, narrowed by the Tenant's allowlist. Adding a host to a space cannot broaden that allowlist. At use time, the effective hosts are the intersection of the space and current Tenant lists; execution runtimes must enforce that intersection. Resource and daily traffic settings are capped by current Deployment ceilings at use time; new defaults are capped when created. Data sent to allowed hosts is outside Aidash's data protection guarantees.

A space may choose an execution image and External services. Without an image it uses the Tenant's default. Image references are pinned by digest and must be approved for the Tenant in the Deployment configuration. Tenant-managed image approval is part of the image lifecycle work. External services are shared with every member of the space; their credentials remain at the Egress gateway. Docker is available only when the Deployment operator permits it for the Offering or Tenant, and then only when the space enables it. Docker-enabled Pods must run on nodes dedicated to that Tenant. Clear keeps the space active and records a new wipe generation for its disposable contents. Delete marks it unavailable and also requests a wipe. The Execution Pod runtime must consume each wipe generation before allowing access to its contents. After idle expiry, the next authorized Run requests a wipe before using the space again. Expired spaces remain visible to their members. The list returns at most the 500 newest spaces available to the caller on the selected Node. The Execution Pod runtime must consume the wipe request before allowing access. Node and Tenant purge remove their spaces.

The Tenant policy action `scratch.create` controls space creation and is allowed to Tenant users by default. Deployment Administrators have no Tenant authority to read spaces.

## Operator configuration

The `[deployment]` settings `scratch_capacity_bytes`, `scratch_cpu_millis`, and `scratch_memory_bytes` set ceilings. Capacity defaults to a ceiling of 1 TiB; the CPU and memory defaults are 4,000 millicores and 16 GiB. `scratch_daily_sent_bytes` and `scratch_daily_received_bytes` set per-day egress ceilings, each defaulting to 1 TiB. `scratch_docker_allowed` enables Docker for the Offering, and `scratch_docker_tenants` lists additional Tenants for which Docker may be enabled. `scratch_all_hosts_allowed` controls whether the Offering permits choosing all hosts. `scratch_tenant_hosts` maps Tenant names to their permitted host lists; a one-element `['*']` list represents all hosts. Without a Tenant entry the public-registry defaults apply. `scratch_tenant_images` maps Tenant names to approved image references.

## HTTP API

`POST /api/workspaces` and `POST /api/conversations` accept optional `scratch_space_id`; omission creates a dedicated space on the Workspace Node in the same admission transaction. `GET` and `POST /api/scratch-spaces` list and create spaces. Creation accepts a Node, name, and optional settings; when settings are omitted the defaults are narrowed to the Tenant allowlist. `GET` and `DELETE /api/scratch-spaces/{id}` read and delete one. Settings are updated with `PUT /api/scratch-spaces/{id}/settings` using the last observed revision; stale updates return HTTP 409. Members are added with `POST /api/scratch-spaces/{id}/members` and removed with `POST /api/scratch-spaces/{id}/members/remove`; both accept a subject. `POST /api/scratch-spaces/{id}/clear` clears it. `GET /api/scratch-spaces/limits?node=...` returns effective ceilings and the Tenant allowlist for the Node. Each operation requires Tenant authority and applies the space's membership and Node checks.
