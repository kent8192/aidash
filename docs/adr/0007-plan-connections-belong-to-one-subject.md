# Plan Connections belong to one subject, not to a Tenant

Decided on 2026-10-09. A Plan Connection from Sign in with ChatGPT belongs to one subject in one Tenant. Only Runs whose delegation chain starts at that subject may draw on it. This is a deliberate exception to ADR 0001, which binds Provider Credentials per Tenant. A ChatGPT plan allowance is personal, and OpenAI's terms forbid sharing it. A Tenant-level binding would let every member spend one person's plan.

## Considered Options

- Treat the connection as a Provider Credential with a Tenant binding. Rejected because it shares one person's allowance across the Tenant.

## Consequences

Revised on 2026-10-13 after the #159 grilling, which checked OpenAI's Sign in with ChatGPT documentation and applied ADR 0028's Deployment, Tenant and Node structure. ADR 0031 records how the authorization callback reaches the server. Revised again on 2026-10-15 to settle enablement, owner notification and the lifecycle hooks against ADR 0041, 0043 and 0044.

- The `chatgpt` Provider Catalog entry is served by the Run's Plan Connection, never by a Provider Credential Binding.
- Plan usage reaches only OpenAI's Responses API, so Aidash needs a Responses adapter beside its Chat Completions path. The first version supports the Legacy and Ordered Projection Versions, function tools, and text and image input. The Native Projection Version and round-tripping reasoning items are separate work (#249).
- Plan Connections exist only on Self-hosted Deployments for now. Cloud and Dedicated are paid, hosted apps that need OpenAI's approval, and OpenAI documents no hosted plan-usage flow, so their builds do not mount the Plan Connection endpoints. The hosted path, including the Credential Broker extension, is separate work that waits for that approval (#248).
- On a Self-hosted Deployment the capability is off by default; whoever runs the Deployment turns it on in the server configuration, because enabling it is consent that the host will hold Plan Tokens it can read. A server whose Provider Credential Store is in Secret Manager refuses to start with it on. Turning it off again stops new authorizations, model lists, admission of `chatgpt` models and plan calls, but owners can still see and disconnect their Plan Connections, and Plan Tokens are kept until they do. The connect screen states that whoever runs the Deployment's host can technically read the Plan Tokens, because the application host reads the Store (ADR 0008). It also states that a Run that compacts its context sends that history to OpenRouter under the Tenant's binding (ADR 0041).
- Plan usage is authorized only when the token response grants `chatgpt.tokens.use.direct`. The ID token carries no sharing flag.
- A Run may use a Plan Connection only when its delegation chain starts at the owning subject. This includes event-triggered and scheduled Runs admitted on that subject's behalf, and child Runs in the same Node. Tenant maintenance and chains that start at a service subject never use one.
- A Plan Connection never leaves its Deployment. It serves Runs in any Node of its owner's Tenant, but never a Run that arrived through Federation, even from another Node of the same Tenant.
- A subject that more than one External Identity is mapped to cannot hold a Plan Connection, and a second Mapping to a subject that holds one is refused until it is disconnected. Otherwise two people could spend one person's plan.
- A Plan Connection records the External Identity that connected it; a reconnection re-records it. The connection serves calls only while that identity is the only active one mapped to the subject, so restoring another mapped identity while the owner is disabled never hands it the owner's plan (#315). It is retired once that identity holds no enabled Mapping to the subject, whatever other Mappings remain.
- Identity Disablement pauses a Plan Connection and keeps its Plan Tokens. Removing the owner's Mapping, leaving the Tenant, and recording a Tenant Deletion revoke the grant at OpenAI and delete the Plan Connection; a Tenant restored from deletion needs reconnection. Leaving and Tenant Deletion (#239) call the revocation that #159 provides, before any purge. A Run admitted before a disconnection fails at its next call.
- A Plan Connection never falls back to a Provider Credential, nor a Provider Credential to a Plan Connection. An exhausted plan allowance or per-app limit (`subscription_sharing_usage_limit_exceeded`) fails the Run with a link to ChatGPT's usage settings, and no paused state is stored, because OpenAI gives no reset time. Temporary unavailability is retried with the usual bounded backoff. An ineligible plan marks the connection unusable and notifies its owner without asking for reconnection. A rejected refresh, or a revocation it confirms, discards the Plan Tokens, marks the connection as needing reconnection and notifies its owner. OpenAI does not report a disconnection made in ChatGPT's settings until a call or refresh fails. Aidash has no push notification channel, so notifying the owner means showing the state in their ChatGPT plan settings and in a dashboard banner while it lasts, and giving the failed Run that reason.
- The server refreshes Plan Tokens only when a call needs them, serialized per Plan Connection, because each refresh rotates the refresh token. A connection unused for 30 days needs reconnection. Background keep-alive refreshes were rejected because they would be maintenance touching a Plan Connection.
- Zero data retention is required wherever the provider path supports it (decided on 2026-10-09). OpenAI offers no zero-data-retention option for plan usage (checked on 2026-10-13), so plan calls send `store: false` and `stream: true` only, a documented exception to the rule that every OpenRouter call enforces `provider.zdr = true`.
