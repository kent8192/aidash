# v0.1.0 nonfunctional release requirements

Status: **decision draft**, 2026-09-28. The [Notion nonfunctional page](https://app.notion.com/p/3e172fa877aa809a9223edf57a313dc5) was blank when this draft was prepared. This document defines measurement and evidence contracts, and lists product and operations decisions that must be agreed before it can become a release gate. Source inspection used `8c8b10f05a89e50b3ad99f9dc8444a331c9abd25`; no load, availability, or restore acceptance run is claimed here. Issue #73 tracks approval and evidence. Issue #67 separately controls any change to the mandatory v0.1.0 functional scope.

## Deployment and workload boundary (NFR-PROFILE-001)

The local Compose and kind installations are development profiles. They use fixture credentials, local volumes and disposable data, and have no availability claim. The release candidate profile is two independently identified Aidash Nodes on Kubernetes, with separate PostgreSQL databases, server and worker roles, persistent JetStream and PostgreSQL-native memory with pgvector/PGroonga and an independently retained Home recovery ledger, protected secrets, and reachable TLS peer endpoints. The [orchestration runbook](../orchestration.md) describes the deployed components. The current `scripts/test-cluster.sh` scenario exercises four tasks, four artifacts and three external effects; that is a functional fixture, not a supported workload size or a throughput benchmark.

Before claiming a supported profile, record the exact deployment manifest and resource limits, replica counts, PostgreSQL/JetStream and external memory-ledger topology, region, network, model/embedding fixtures, image digests and tested revision. Approve concurrent human sessions, active Agents, concurrent runs, and the supported Node count. Test those maxima together rather than extrapolating from HTTP rate or worker-slot defaults. Larger scale and other cloud/topology combinations remain unverified until measured. This boundary does not remove the mandatory A2A, authorization, transaction or six-capability release gates.

The GCP profile uses shared GKE Standard and pinned upstream gVisor on Ubuntu
Cluster Nodes. Its single-attach ledger, PostgreSQL, NATS and Runner journal
recover through rescheduling and disk reattachment, with a service pause.
Cluster Node loss and drain leave unproven in-flight operations uncertain.
The gated idle seal drains server and worker while retaining the Runner for the
final activity observation; work admitted after the last idle observation can
be interrupted even without `force`. Real GKE loss/reattachment and full release
acceptance remain unverified until their approved drills run.

## Service behavior and performance

**NFR-PERF-001 — Latency and throughput.** Agree p50/p95/p99 and minimum sustained successful requests per second separately for authenticated workspace reads, task mutations, scoped federation commands, semantic search and SSE connection/replay. Report provider inference and external Tool latency separately; do not hide Aidash admission, policy, database, queue or serialization time. Use fixed seeded data and the approved NFR-PROFILE-001 concurrency; warm up, then run at steady load for an agreed duration at least three times. Report each run's requests, successes, 4xx/5xx, timeouts, latency histogram, resource saturation and traceable revision. A run passes only if **every** metric's agreed limit holds in each repetition. The targets and load driver remain decisions below.

**NFR-AVAIL-001 — Availability and dependency outages.** Agree a monthly availability target, the probe endpoint and denominator, the allowed error budget and maintenance treatment for each deployment profile. Count an authenticated representative API journey as available only when its required response is correct; `/live` alone is insufficient. Inject PostgreSQL, JetStream, external memory-ledger, identity-provider and selected model-provider outages independently and restore each. PostgreSQL loss must remove readiness and prevent unsafe writes. JetStream loss must leave a durable PostgreSQL outbox and drain it after recovery. Loss, corruption or closure of the external memory ledger must make native memory unavailable without unauthorized or stale fallback. Projection failures require rebuilding from current PostgreSQL authority. OIDC outage behavior follows the [authorization contract](../authorization.md), including the distinct Keycloak and Google limits. External inference may fail or pause explicitly; its availability is measured separately from the Aidash API. No outage is counted as passed until durable work and user-visible status are reconciled.

## Recovery, retention and protection

**NFR-DR-001 — Backup and restore.** Agree RPO and RTO for loss of one Node's durable services and for loss of the complete two-Node deployment. The clock begins at the fault; RPO compares the last _verified restorable_ state to the last acknowledged write, and RTO ends only when authorized read, write, execution recovery and semantic search pass. Backups must cover each Node's PostgreSQL data (including tasks, runs, journals, artifacts, policies, source memory, transaction decisions, outbox and cleanup records), JetStream storage or an explicitly validated outbox replay path, PostgreSQL semantic projections or deterministic rebuilding, and each Home's independently retained memory epoch/revision/deletion ledger, deployment configuration and separately protected credentials. Define backup cadence, encryption, off-site copies, immutability, access controls and retention before accepting a target. A database dump alone is not an end-to-end backup.

Repeatable isolated restore drill:

1. Record image/revision, topology, backup IDs and timestamps, transaction status, event high-water marks, task/run/artifact IDs, semantic source IDs and a fixture's exact expected contents. Use two independent Node databases. Quiesce new writes and wait for admitted cross-node transactions to finish before taking a coordinated _baseline_ backup; otherwise the two backups have no proven common transaction cut. Preserve the PostgreSQL backup and matching configuration outside the cluster. Record the separate credential-vault version without copying values into evidence.
2. Restore into a new isolated namespace/cluster with no access to production peers or secrets. Restore both PostgreSQL databases and either matching JetStream storage or an empty broker **only** after verifying the persisted outbox replay path. Preserve each Home's current external memory recovery directory independently; never rewind its epoch/revision/deletion ledger with the database snapshot, replace a missing ledger, or initialize a restored nonempty Home. Full PostgreSQL authority/control rewind remains outside the managed memory-only recovery profile and needs separate continuity validation before native memory can serve. Start compatible migrations/runtime versions and check transaction decisions before reopening work.
3. Restore credentials through the approved secret manager, then verify authorized and denied API reads, task/run/artifact IDs and contents, transaction status, event replay, pending outbox delivery, and recovery of safe/idempotent work without duplicate external effects. Rebuild missing PostgreSQL semantic projections from current canonical sources under current authority and confirm that deleted/revoked sources stay absent. For managed memory-only recovery, follow [memory recovery](../memory-recovery.md): close the persistent serving gate, restore a valid managed archive against the retained ledger, and reopen only through successful reconciliation. Initialize a recovery directory once only for an empty new-format Home; subsequent bootstrap must use `init-if-missing` to validate and preserve existing state. Unsafe effects require reconciliation rather than automatic replay.
4. Record last acknowledged and last recovered writes, elapsed time, missing/extra records, failed checks and operator actions. The drill fails if either agreed RPO/RTO is missed or any security, consistency or idempotency check fails. Test a backup newer than the last confirmed cross-node transaction cut separately before allowing online, unquiesced backups to satisfy this requirement.

**NFR-DATA-001 — Retention and deletion.** Approve periods and legal-hold rules separately for workspace content/artifacts, execution journals and events, authorization/audit decisions, semantic sources and vectors, recovery snapshots, backup copies and operational logs. Active runs, unresolved transactions, pending outbox entries and outstanding deletion jobs cannot be silently truncated. Deletion must remove authorized source visibility immediately, complete downstream PostgreSQL projection and quoted-body cleanup and backup expiration under the approved schedule, and preserve only explicitly required audit data. Test normal expiry, explicit deletion, restored backups, failed cleanup and retry; record which stores still contain recoverable bytes. Existing semantic tombstones and core working-area cleanup are component behavior, not a global retention policy.

**NFR-SEC-001 — Data and credential boundary.** Require TLS for public, peer, database, broker and semantic traffic across trust boundaries; keep `AIDASH_SECRET_*` values in a protected secret manager and out of Registry records, logs, test evidence and Git. Define at-rest encryption and backup-key ownership for the approved profile. Exercise revocation, peer mapping changes, tenant isolation, least-privilege backup/metrics access and restore from an old authority snapshot. A restored snapshot may reintroduce earlier permissions; keep the restored deployment isolated until current policy, credential and peer trust are reconciled. The [authorization](../authorization.md) and [HTTP observability](http-observability.md) documents define current mechanisms, not proof that the deployment meets this gate.

## Monitoring and alert acceptance (NFR-OBS-001)

Scrape the private Prometheus endpoint and correlate request IDs with sanitized logs. Record availability and latency by route/status, 429/503/504 rates, live SSE bodies, worker activity/retries, model header latency, PostgreSQL connection/readiness state, outbox and inbox lag, JetStream delivery, transaction reservations/recovery waits, semantic indexing/cleanup failures, pgvector/PGroonga projection health, external memory-ledger serving gate and pending purge jobs, backup age and failed restore drills. The [HTTP metrics](http-observability.md) cover only part of this list; database/broker/projection/recovery-ledger and backup signals need a documented collector or query. Do not use tenant, subject, run ID, arbitrary path or secret values as metric labels.

For each critical condition, approve threshold, hold time, severity, notification destination, responder and acknowledgment deadline. Inject at least one fault for each dependency and one backup/restore failure. Record the alert firing time, delivery receipt, acknowledgment, linked runbook and resolution signal; an unobserved failure or an alert with no owner fails acceptance. Never infer alert coverage from the mere existence of a metric.
