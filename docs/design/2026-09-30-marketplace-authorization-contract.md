# Subject-scoped Marketplace authorization contract

Status: accepted at the final shared-understanding confirmation. Q1-Q14 in the [decision record](2026-09-30-marketplace-authorization.md), this contract and the [installed Registry mapping](#installed-registry-mapping) are accepted. They define the agreed implementation contract; they do not claim implementation or runtime acceptance.

Issue: [#74](https://github.com/kent8192/aidash/issues/74). Target: `develop/0.1.0`, milestone `v0.1.0`. The inspected baseline is `827480c13d796bca142787be5bbd25ce34c80551`. FR-MKT-001 through FR-MKT-004 and FR-AUTH-001 remain mandatory; this design does not change the release scope in #67.

## Domain and resource identity

| Resource                      | Identity and authority                                                                                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Package family                | Repository Node, owner tenant and package identifier. Same names in different owner tenants are independent.                                                                     |
| Package version               | Exact package family plus semantic version, immutable source manifest and digest. Publishing a new version does not overwrite or inherit a prior version's audience.             |
| Distribution audience         | Revisioned owner-controlled membership of named recipient tenants for an exact package version. Initial audience is the owner tenant only.                                       |
| Redistribution consent        | Revisioned source-owner permission for an exact source version, redistributing tenant and intended onward audience. It is separate from sharing for local use.                   |
| Tenant installation           | Stable local identity for an installing tenant and qualified source package version. A retry finds this binding; it cannot attach to another tenant's same-named entry.          |
| Installation revision         | Immutable local configuration and exact dependency bindings for that installation, with a digest of the resulting installed definition.                                          |
| Installed Registry definition | An immutable, tenant-bound Registry reference for one installation revision. Source identity and package version remain separately visible as provenance when authorized.        |
| Approval and activation       | Approval permits use of the exact installed reference; a revisioned active pointer selects the approved revision for new Runs. Older approvals may remain valid for pinned Runs. |
| Legacy resource               | An existing package or installation without tenant ownership, retained under explicit operator authority.                                                                        |

Use a validated, unambiguous encoding or a persisted opaque policy key with a unique mapping to the qualified identity. Policy keys must fit the existing identifier limits; naive concatenation, editable display names and author strings are not authority identifiers. A family cannot change its owner tenant, identifier or entity kind by publishing another version. A new owner or identity requires a distinct authorized publication/adoption with retained provenance.

Tenant and subject come from the authenticated context. The server resolves persisted ownership, publisher provenance, sharing, source references, installation tenant/revision and dependency bindings. Requests cannot replace those attributes. Display authorship and declared package permissions are metadata, not grants. The canonical trusted attributes include repository Node, owner tenant, package identifier, version, kind, source digest, publisher actor, installing tenant, installation revision and effective-definition digest as appropriate to the resource. Existing validated Registry metadata supports ABAC; payload fields cannot masquerade as ownership or consent.

### Installed Registry mapping

Allocate an immutable Registry reference for each tenant installation revision. Preserve source manifest bytes and their digest separately; rewriting local IDs, binding dependencies or adding local configuration changes the installed definition's digest, never the published digest. Any physical deduplication is limited to immutable content and cannot merge tenant ownership, configuration, approvals or mutation authority.

Each typed source reference is resolved to an exact local dependency binding in the installing tenant. Never resolve a same-named entry from another tenant or an unrelated legacy namespace as a fallback. The installed definition's references point to the pinned local definitions. A dependency-binding change is an effective configuration change requiring a new installation revision and approval, even if the package version and submitted overlay are unchanged.

The resolver must cover normal API reads, Registry discovery, worker and tool loading, activation/resume, source export and existing remote execution pinning paths. An unscoped Registry lookup is not a substitute for resolving a tenant installation. Existing immutable Registry references for unrelated native entries retain their current behavior.

## Authorization and action matrix

Default deny, explicit-deny precedence, RBAC role/group inheritance, ABAC and delegation-ancestor restrictions apply at every checked boundary. User, Agent, Node and service subjects use the same policy semantics. Owning a package, being its publisher, belonging to its tenant or receiving a sharing grant does not create an implicit action permission.

For a recipient, evaluate actions in the authenticated recipient tenant's policy domain with the qualified source identity and trusted `owner_tenant` attribute. Separately require authoritative audience membership and source consent where relevant. Never interpret a recipient's same-named subject as a subject in the owner tenant. Editing audience or consent requires the acting subject to belong to the owner tenant and pass the owner-side permission checks.

The action names below are the accepted policy contract. Permission implications are explicit; no role is automatically populated with them.

| Operation                              | Required authority                                                                                                                        | Resource and result                                                                                                                                                                           |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browse/search                          | `marketplace.browse` and live distribution gates                                                                                          | Exact candidate package versions; return authorized summaries only. Browse does not grant full read or install.                                                                               |
| Read exact definition                  | `marketplace.read`, live distribution gates and permission to disclose every referenced definition                                        | Exact package version. Direct read need not grant enumeration. Return the full immutable manifest or a generic denial.                                                                        |
| First installation                     | `marketplace.read`, `marketplace.install`, local `installation.create` and `installation.read`, plus dependency read/management authority | Source version and prospective destination installation fixed to the authenticated tenant. Create one pending revision; no catalog approval is granted.                                       |
| Read/manage installed data             | `installation.read`, with current read authority over included local dependencies                                                         | Tenant installation and selected revision. This management view may include a pending revision; it grants no Registry discovery or execution access.                                          |
| Change configuration                   | `installation.read` and `installation.configure`, plus authority to read/bind dependencies                                                | Existing tenant installation. Create a pending revision without changing the active one. Source Marketplace access is not required to configure a committed local copy.                       |
| Publish                                | Current source `registry.read` and `registry.export`, plus `marketplace.publish`                                                          | Exact registered source and destination family/prospective version. Read source data through existing Registry authority, not a request-body substitute or an installation-management bypass. |
| Change sharing                         | `marketplace.share`                                                                                                                       | Exact version owned by the acting subject's tenant, with optimistic audience revision checks.                                                                                                 |
| Grant/revoke redistribution consent    | `marketplace.redistribution.manage`                                                                                                       | Exact source version owned by the acting subject's tenant; name the redistributing tenant and onward audience.                                                                                |
| Redistribute an imported definition    | Publication checks above plus all applicable live source consents                                                                         | Preserve known source lineage and ensure the publication's audience is permitted by every source.                                                                                             |
| Approve, activate or revoke a revision | Existing explicit operator catalog-administration authority                                                                               | Exact installed Registry reference and active-pointer revision. Installation permission cannot self-approve.                                                                                  |

A pinned Run may still read its specifically approved older references.                              |
| Execute                                | Current catalog approvals and existing action checks for each actual boundary                                                             | Pinned definitions plus `agent.execute`, `model.infer`, `tool.invoke`, `skill.use`, `cluster.execute` and task/workspace/run permissions as applicable.                                       |

Source publication requires ordinary authorized Registry access. Registering a definition or being able to inspect a pending installation is not a shortcut around that read/export requirement. Existing dedicated Creator management permissions retain their endpoint-specific scope.

An explicitly selected operator context retains privileged administration, legacy operation and recovery. Tenant-subject requests never silently retry as operator. Operator administration of tenant resources names the tenant explicitly and records the operator actor; it cannot reinterpret display authorship as tenant ownership.

## Publication, sharing and redistribution

Subject publication selects an exact stored Registry reference. The server obtains its immutable distribution source, validates its type and metadata, and checks source read/export and destination publication authority. Installed-definition provenance supplies the preserved distribution source rather than exporting an effective local override. Do not resolve credential values into manifests; reject unsupported embedded secrets and retain existing secret-reference validation without exposing secret availability through scoped errors.

Resolve and authorize declared dependencies and typed references before publication. References embedded in Agent configuration, tools, skills, clusters and supported attachments count even if omitted from the submitted dependency list. The publisher must have authority to disclose the emitted source metadata, and imported sources require consent for the proposed audience. A dependency list cannot conceal references that the definition itself contains.

Persist manifest bytes, source digest, authenticated publisher, ownership, source/dependency lineage and initial audience atomically. An identical authorized retry returns the existing result without another publication/event. A different manifest under the same qualified version is an immutable-version conflict only after the caller is entitled to learn about that version. New versions require publication authority and explicit audience selection.

Audience and consent changes are revisioned and audited separately from immutable manifest bytes. They cannot rewrite the version or its digest. Revoke and grant operations use expected revisions so concurrent changes cannot silently overwrite each other. Publisher credential revocation prevents new actions by that actor; previously created audience/consent records are controlled through their own explicit withdrawal, not the publisher's continuing login session.

Widening an audience rechecks source disclosure and all upstream redistribution consents for each intended recipient before committing the change. A subject cannot use sharing changes to add an audience that publication of the same content would have been forbidden to reach.

Every subsequent distribution read/acquisition, including an already published downstream package's summary, rechecks all applicable source consents and audiences. A broken, withdrawn or invalid source-consent chain fails closed. Known platform copy, duplicate, import and derive workflows retain lineage; clients cannot clear it in a payload. This contract governs known provenance and does not claim to infer arbitrary content ancestry from manually re-entered text. Provenance traversal must be bounded and reject malformed or cyclic consent chains.

Distribution withdrawal hides affected Marketplace content and prevents new acquisition, publication and onward distribution. It does not revoke the recipient's independent authority over a committed installed copy. Reading/configuring that local copy still requires current tenant management permissions; executing it still requires current catalog and execution authority. Local copies never acquire an automatic redistribution right.

## Browse, dependencies and non-disclosure

Separate summary responses from full manifest responses. A summary contains only metadata permitted by `marketplace.browse`; it does not embed configuration, raw dependency references or installation data from another tenant. A subject authorized to see a summary may see that package even if a dependency prevents full read/install. Return no hidden dependency name, ID, metadata, count or specific denial reason.

Filter by audience, consent and policy before calculating visible page counts, cursors, facets or suggested values. Filter fields based on model/skill/dependency references require authority over the referenced information; they cannot be used as membership probes. Fill page limits with authorized candidates, not with a sparse page that exposes hidden candidates. Cursor contents must not expose another tenant's keys or raw offsets into an unfiltered set.

Full-manifest read requires authority over every reference it would disclose. A dependency may be readable through a live Marketplace disclosure path or through the caller's already installed/registered tenant copy, as appropriate; dependency preparation is required for installation, not merely to discover an otherwise readable package. Do not return a redacted manifest under the original digest. Authorized summaries and complete immutable manifests are distinct representations.

Installation requires every dependency to be already registered or installed for the receiving tenant and readable through its permitted Registry/installation management path. Management access to pending local dependencies may support staging; it does not authorize their execution. Validate exact identity, kind, version and content bindings, including typed and transitive references according to the supported definition graph. Missing/inaccessible dependencies reject the root operation; no dependency is fetched or installed implicitly. Traverse shared/cyclic references safely within existing supported graph semantics, with bounded work and no authorization bypass.

## Installation revisions and execution

Before writing, verify the caller-supplied expected package digest against the stored immutable source bytes, validate source consistency, resolve the destination tenant and dependency bindings, and validate the effective configuration. Keep the existing restrictions on overrides of immutable knowledge, capabilities and attachments. Scoped validation must not reveal the contents or existence of node secret values.

Commit the installed Registry definition, source mapping, installation revision, configuration, dependency bindings, idempotency result and appropriate success event together. Failure or a denied authority check leaves none of those success records visible. A separately persisted denial audit is not a partial installation. First installation produces a pending revision and cannot change any catalog approval or another tenant's active configuration.

For configuration changes, compare the current installation revision using an optimistic precondition. Repeating the same content returns the same result without a new revision/event. Changing effective content, including a dependency binding, creates a distinct immutable pending revision. Approval binds the exact resulting definition/digest and its fixed dependency set; an unchanged package version cannot reuse an older configuration's approval.

An operator may approve and activate a prepared revision with a revision-checked operation. Activation validates the exact installed definition and required dependency approvals and atomically selects it for new Runs. Earlier approved revisions remain retained and individually revocable; activating a replacement does not by itself revoke them. Revoking the active revision leaves new execution blocked until an explicit authorized activation, rather than silently falling back to an older revision.

At admission, pin the complete exact definition set selected for the Run. A new Run uses the active approved revision; an admitted Run continues using its pinned approved revision and dependencies, including after process restart. Re-resolving an active alias must not mutate its execution. Every existing worker/read/effect boundary checks current subject authority and approvals for those exact pinned references. Revocation pauses affected work at the next boundary; it does not undo an already performed external effect or substitute another configuration during resume.

Allocating an installed Registry reference does not create or enable a privileged Agent policy subject or copy another definition's subject grants. Existing exact Agent-subject and delegation checks remain required; the policy administrator configures the corresponding identities and permissions explicitly. Physical reference mapping must not silently transfer principal authority.

Retain source content, prior installed revisions and provenance needed by approvals, admitted Runs, idempotency and audit. This change introduces no automatic destructive cleanup. Publication versions remain immutable even when their audience changes or all local execution approvals are withdrawn.

## Durable and response boundaries

| Boundary                                      | Required behavior                                                                                                                                                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request admission                             | Validate credential/session/mapping and authenticated tenant/subject; validate resource-independent input shape without looking up inaccessible data.                                                            |
| Candidate selection and dependency resolution | Resolve trusted resource state; apply policy, audience and consent gates before including data or resource-dependent errors.                                                                                     |
| External/unlocked wait                        | Do not carry a cached allow decision across the wait. Reacquire current authority and verify frozen identities/digests before further reads or writes.                                                           |
| Mutation commit                               | Recheck/retain the current credential, policy, ownership, sharing, consent and dependency authority until the atomic commit boundary. Serialize competing revocations and mutations on the same protected state. |
| Response handoff                              | Recheck current disclosure authority for the actual serialized response. Use a bounded response handoff ordered against revocation, not authorization only at handler entry.                                     |
| Replay, state and SSE delivery                | Re-evaluate the current reader and underlying resource gates for each disclosed result/frame. Unknown/legacy unscoped event families remain withheld from subjects.                                              |
| Worker and resume                             | Recheck live authority for the Run's pinned installed references; a prior install or approval does not authorize later effects after revocation.                                                                 |

Use deterministic lock ordering and existing authority-lease patterns to avoid deadlocks with policy, credential, sharing, consent and catalog revokers. Scope and resource state must not be checked in an independent transaction that can become stale before a protected write. Reads must not expose data from a failed or uncommitted installation.

If a mutation's protected boundary wins the ordering, it commits before revocation completes; if revocation wins, the mutation produces no installation/publication changes. A request's start time is not a durable grant. Test both orderings with deterministic barriers.

The response guarantee is at bounded disclosure handoff: a committed revocation prevents a later response/frame from being newly authorized and queued. It cannot retract bytes already handed off while authorized. Do not hold database locks for an unbounded client's network drain; ensure the implementation has an explicit bounded handoff instead of claiming that a check followed by arbitrary serialization is race-free. A committed mutation may outlive the caller's right to see its response; in that case withhold protected response data and let a subsequently authorized installation read reconcile the outcome.

Idempotency records are scoped to tenant, authenticated principal and operation, with a request fingerprint binding qualified source identity/digest, destination, configuration and expected revisions. Replays reauthorize current access and return only currently visible results; they do not replay cached allow decisions. A new valid credential for the same principal may retry under current authority, but another principal cannot claim its result by guessing a key. Changing a request under the same key is a conflict only when disclosing that conflict is authorized.

## API, errors and dashboard

Retain legacy operator routes and payload behavior in their legacy scope. Add qualified subject operations with explicit summary/detail representations, registered-source publication inputs, source digest checks and revision preconditions. Bare legacy `id/version` routes must not guess a tenant or search across tenants. Update OpenAPI, generated client types and API operation-count assertions together with handler changes; wire encoding may use stable opaque handles mapped to the qualified identities above.

| Situation                                                                       | Subject response                                                                                                                                     |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invalid, expired or revoked authentication                                      | Existing HTTP 401 behavior; clear authenticated dashboard state.                                                                                     |
| Missing, other-tenant, hidden or unreadable target/dependency                   | Uniform HTTP 403 with a generic resource-unavailable message; no hidden identifier, existence distinction, policy IDs, revision or dependency count. |
| Authorized immutable-content, digest, idempotency or expected-revision conflict | HTTP 409 with actionable information limited to data the caller may read.                                                                            |
| Resource-independent malformed input                                            | Existing HTTP 400/422 validation conventions, without consulting or echoing hidden resource state.                                                   |
| Authorized empty search                                                         | HTTP 200 with an empty visible collection; no total from the unfiltered repository.                                                                  |

Gate resource-dependent validation errors as carefully as successful responses. Authenticated package/installation responses use `Cache-Control: no-store`. Logs and operator-only audit may record detailed causes within their authorized scope; subject responses and activity events must not copy those details.

Provide a Marketplace entry point for scoped users, authorized summary search and a details view that fetches current full-read authority. Display only currently allowed actions, using server-evaluated permissions; every mutation still checks independently. An inaccessible dependency produces a generic unavailable-details/install state, without identifying the dependency or how many dependencies were rejected.

Provide tenant installation management independently of execution discovery. `installation.read` can show pending and retained revisions without admitting them to ordinary Registry search or execution. Show the active and pending revisions separately; configure requires its own permission. Catalog approval and recovery remain explicit operator workflows. Subject publication selects an authorized registered source, previews the exact version and audience, and does not accept arbitrary replacement definitions or offer sharing without its separate permission.

## Existing data, migration and recovery

Migrate additive ownership, installation-revision, source-mapping, audience, consent, idempotency and audit metadata without rewriting existing immutable manifest bytes or digests. Existing unowned packages and node-wide overlays remain legacy operator resources; no tenant claims them through first access or a matching display author. Avoid changing unrelated user data or inventing initial sharing grants.

An operator may explicitly adopt a selected legacy source into a named tenant. Verify the source, create a distinct qualified package/installation mapping, preserve provenance and local configuration as an independent pending revision, and require fresh tenant approval. Copying cannot retain a mutable link to the node-wide overlay. Retrying adoption is idempotent and preserves the original legacy source.

Existing explicit catalog grants to native/legacy Registry entries retain their original Registry meaning. They do not imply Marketplace ownership, permission to mutate a legacy overlay or approval for a new tenant installation projection. Prevent a catalog binding in tenant B from directly approving tenant A's installed definition; use explicit authorized adoption into B instead.

Fence activation of the new subject paths until all serving instances and workers recognize the ownership and revision contract. Mixed-version requests must fail closed for unsupported tenant resources rather than interpreting them as legacy/global rows. Preserve compatible legacy operation during rollout; document the compatibility gate and reject unsupported old writes instead of silently dropping ownership or revision checks.

Use SeaORM/SeaQuery for schema changes and queries. Any DDL that cannot be expressed through SeaQuery requires the repository's documented exception. Audit records retain authenticated actors, qualified identities, request IDs, policy/sharing/consent/configuration revisions, digests, outcomes and bounded reasons; they contain no bearer tokens or resolved secret values. Denial audits survive failed mutations without exposing the data to an unauthorized subject.
