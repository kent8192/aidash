Status: accepted, 2026-09-28. All fifteen decisions from the three interview rounds are accepted. The user confirmed the complete design by requesting implementation after the final synthesis. ## Scoped authority and observation

Transaction permission is additional to ordinary mutation authority, not a replacement for it. Workspace updates require the applicable workspace read/update checks; Task completion requires task access, `task.complete` and `artifact.create`; Run finalization must preserve ownership and the admitted Home/Executor pairing. Both source and receiver independently enforce the originating chain and mapped authority. Subject tokens and secret values must not be forwarded. Operator submission retains the existing supported mutation set, including Registry registration.

Ordinary execution still checks live authority at subsequent execution boundaries. Only the fixed, already admitted transaction obligations use the D2 exception; recovery cannot introduce new mutations, new resources, a new manifest or a substituted subject. Resource reads, transaction details and user event delivery continue to use current authorization. A recorded COMMIT cannot be undone by subject or operator abort.

A read before the transaction and another independent read after publication need not share a snapshot. The atomicity oracle instead checks that uncommitted or incompletely applied results do not escape through any supported ordinary API, Worker or event boundary. Once any Participant exposes this transaction's new state, another Participant must not serve this transaction's old state through a new ordinary operation; it may remain unavailable until its barrier is released. Already delivered values cannot be retroactively withdrawn.

The no-duplicate criterion applies to durable mutation effects, Artifacts and logical event records. It does not promise that a retrying transport sends one packet or frame. Retries retain stable logical identity, and duplicate delivery must not produce a second consumer effect.

Unsupported external Tool, provider and nonparticipating A2A effects remain excluded from manifests and must be rejected before Coordinator submission or Participant reservation. A forbidden mutation kind must not be silently dropped from an otherwise accepted manifest. Ordinary external execution keeps its separate durable-execution contract; this design does not introduce a transactional external adapter. Scoped Registry registration is likewise rejected rather than elevated to operator authority.

## Admission, revocation and disclosure ordering

Participant admission is the authority boundary, not an HTTP response, an in-memory permission check or a coordinator's initial submission. Bind the originating chain, mapped identity, exact manifest, relevant authority revisions and resource obligations to durable admission evidence. A lost response must be recoverable without a new manifest, substituted identity or second admission. The implementation must prove the ordering across independent databases; a process-local lock or a cached permission result is insufficient.

Revocation has a requested/pending state and a completed state. Once requested, deny new work under the affected authority. An attempt already racing with the request may have been admitted even when its response was lost: resolve that specific attempt from durable evidence before reporting revocation complete. If it won admission, preserve its fixed obligation; otherwise prevent delayed messages from creating it after revocation completion. A partition can delay the acknowledgment of completed revocation, but cannot reopen new business access while it is pending. Ordinary data reads and subsequent execution remain denied by current authority; this does not cancel the admitted transaction's recovery.

The source and each Participant independently apply these rules to their own authority changes. Subject/credential expiry, mapping changes and transaction-trust revocation cannot silently rebind an attempt or create a different admitted subject. A mapping or credential restored later permits only the rights explicitly restored; existing recovery must not depend on issuing a fresh business authorization for an old admitted obligation.

Before transmitting the full manifest, verify that every recipient is entitled to every included payload, including another Participant's updates. Mutation permission and peer transaction trust are separate checks. Preflight must use only the information whose disclosure is already permitted; sending the protected payload to ask whether it can be sent is not valid preflight. Bind the disclosure result to the exact manifest and recipient set, and do not reuse it to disclose a changed manifest or add a Node. Duplicate recovery traffic remains restricted to those admitted obligations and authenticated recipients.

Scoped list/detail responses must not reveal another subject's transaction, revoked resource contents, participant details or a manifest through an error message. The initiator needs current access to every target for full details; an unavailable authority service is not permission to fall back to cached access. Operator recovery visibility remains available with its privileged authorization. User event delivery applies current resource authority even when the underlying event was created by an admitted obligation.

## Control availability and admission pressure

The visibility barrier continues to block ordinary application reads, writes, discovery, Worker effects and streaming delivery. Exempt only the control functions needed to evaluate authority, deny new work, settle revocation, restore the same peer's authentication, inspect authorized transaction status and request undecided abort. Control operations may use protected metadata internally but must not expose an application snapshot or perform unrelated resource mutations. Apply the boundary at both HTTP routing and database write guards; moving a route alone is insufficient. Control capacity must remain usable while ordinary pools are occupied.

Peer communication still requires valid authentication for the recorded Node. Revoking transaction trust does not disable already admitted recovery, but peer disablement or transport credential loss can prevent it. Restore verified communication through the control path without silently restoring subject mappings or transaction trust for new work. Do not provide a force-commit, force-abort-after-COMMIT or manual barrier-clear escape hatch.

For subject submissions, return a retryable busy response instead of queuing new work behind an active required reservation. Preserve the original transaction for an authorized exact-ID retry and never create a second submission for it. If concurrent submissions pass initial checks and a remote reservation later reports a real conflict, an undecided transaction records ABORT and reconciles every acquired or uncertain reservation. An outage, lost reply or unrelated HTTP 503 must not be mistaken for proof that no reservation exists. A durable COMMIT remains immutable regardless of later contention.

Recovery scheduling must retain progress for unrelated work once its required Nodes are free; an unreachable already-aborted transaction must not monopolize the recovery loop or make all later local transactions wait for its remote acknowledgment. Limits and backoff are implementation details, subject to this behavior and the accepted three- and sixteen-Node cases.

## Accepted evidence contract

| Tier              | Coverage required in both Kubernetes and k3s                                                                                                                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Two Nodes         | Every durable protocol transition interrupted immediately before and after persistence, using actual Coordinator/Participant process termination and network faults. Include commit/abort, stale revisions, conflicting manifests, delayed/duplicate messages, retries and independent Node databases. |
| Three Nodes       | Partial partitions, conflicting coordinators and revocation with only some Participants admitted or applied.                                                                                                                                                                                           |
| Sixteen Nodes     | Maximum-participant commit/abort and partial Participant failure/recovery. No throughput or larger-scale guarantee is inferred.                                                                                                                                                                        |
| Cluster lifecycle | Worker scale, role replacement and rolling update while the transaction is in progress, with durable identity and visibility preserved. Distinct-version evidence additionally satisfies D11.                                                                                                          |

Each case must pass three repetitions. The recovery observation interval begins after the injected fault is removed and required services are restored, ends only when all Participants have finalized the same decision and their transaction barriers have been released, and must not exceed 180 seconds. Record fault time, restoration time and completion time separately: this test deadline is not a fault-to-recovery production RTO or an availability SLO. A failure in any repetition remains a failure, not an average that passing repetitions can hide.

During every supported interruption, continuously probe the relevant ordinary boundaries and assert no partial visibility; reconcile exact durable revisions, decisions, Artifacts and logical events after recovery. Also make deterministic observations while a fault hook holds each relevant durable boundary; sampling alone can miss a brief partial-visibility window. A successful exit or healthy Pod alone cannot establish transaction acceptance. Implementation-specific fault hooks will follow the settled behavioral contract; no tier can be silently omitted.

The planned case inventory below is a specification, not executed evidence. Expand each transition family into concrete cases tied to the final implementation, with the owning process, immediately-before/immediately-after durable cut, fault direction and assertion recorded. Coordinator and Participant roles are independent even when a Node performs both; test loss of each owning server/Worker process and restart against retained data, not only dropping a database pool. Independent Node databases must use separate pools and credentials with no runtime reads of another Node's database; acceptance-side privileged inspection is diagnostic evidence, not the protocol.

| Family         | Required boundary or scenario                                                                                                                           | Required outcome                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TX-ADMISSION   | Coordinator submission; source authority-attempt record; Participant reservation/admission; policy, mapping and trust races; lost acceptance reply      | One immutable identity/manifest binding, no admission from stale authority after revocation completion, no duplicate reservation, no ordinary work through the barrier        |
| TX-REVOCATION  | Revocation request, uncertain racing admission and revocation completion; restart or partition at each durable step                                     | New work denied while pending, uncertain outcome retained durably, completion never acknowledged early, admitted obligations remain recoverable                               |
| TX-PREPARE     | Each Participant's speculative validation and durable prepared vote; coordinator acknowledgment persistence                                             | No speculative effects escape; stale revisions and invalid pairings abort; retry cannot change the manifest or vote                                                           |
| TX-DECISION    | Coordinator COMMIT/ABORT persistence, operator/subject abort contention and deadline before decision                                                    | One immutable decision; no timeout-based Participant guess; committed work remains recoverable beyond the deadline                                                            |
| TX-APPLY       | Participant mutation/event application, local APPLIED persistence and coordinator acknowledgment                                                        | Mutation, Artifact and logical event appear once in durable storage, remain hidden before the global visibility decision, and survive lost replies                            |
| TX-VISIBILITY  | Coordinator visibility decision, each barrier release, final acknowledgments and complete record                                                        | No ordinary operation observes partial application; delayed Nodes remain unavailable; completion requires all barriers released                                               |
| TX-ABORT       | Abort application/tombstone and release; delayed reserve/prepare after abort                                                                            | No data effects; delayed requests cannot resurrect an aborted transaction; abort cleanup survives restart                                                                     |
| TX-MESSAGE     | Request/response loss, bidirectional and asymmetric partitions, duplicates, reordering, altered digest and retry after reconnection                     | Authentic messages converge on the durable decision; conflicting identities/digests fail; unknown outcomes remain recoverable                                                 |
| TX-AUTHORITY   | Cross-tenant/mapping mismatch, denied underlying action, source-chain revocation, expiry, peer trust disablement, peer key loss and restoration         | New admissions denied as required, admitted recovery preserved without bypassing peer authentication, current read/delivery access enforced                                   |
| TX-DISCLOSURE  | One unauthorized recipient; changed recipient set; denied preflight; attempt to leak payload through status/errors                                      | No unauthorized manifest transmission or admission; no protected payload in authorization preflight or diagnostics                                                            |
| TX-UNSUPPORTED | External Tool/provider/nonparticipating A2A effect, unknown kind and subject Registry registration in a mixed manifest                                  | Reject the complete request before submission/reservation; no supported subset executed and no external effect invoked                                                        |
| TX-PRESSURE    | Concurrent/opposing coordinators, busy reservation, duplicate submission and unreachable aborted history                                                | New subject requests fail promptly when busy; exact-ID retries retain identity; aborted history cannot starve independent work                                                |
| TX-CLUSTER     | Worker scale down/up including zero and resume, process replacement, same-version rolling update, qualified different-version server/Worker coexistence | Stable Node and transaction identity, retained decisions, no partial visibility or duplicate durable effects; complete within the test observation deadline after restoration |
| TX-DASHBOARD   | Submission/status/abort, pending revocation, unavailable peer, permission loss, reload during a barrier and recovery in English/Japanese                | Authorized controls remain usable; pending is distinct from success; revoked or stale data is hidden; an HTTP 202 is not displayed as completed commit                        |

Repeat commit and abort outcomes where the transition permits them. Once COMMIT is durable, later failure cases must keep COMMIT rather than manufacture an abort branch. Assert HTTP/read behavior and stored outcomes separately; diagnostics must not be counted as ordinary visibility. Retain failed repetitions as failed records rather than replacing them with a later successful rerun.

## Source observations at the interview baseline

The following observations describe `20d1fb46`, before implementation. Current behavior and executed results are recorded in the transaction contract and evidence register.

- `src/transactions/api.rs` applies `operator_only` to transaction administration. Subject admission and subject-filtered management are still design and implementation work.
- `src/transactions.rs` fixes the manifest, supports up to sixteen participants, and defines `registry_register`, `workspace_state`, `complete_task` and `finish_run` mutations.
- `src/transactions/participant.rs` persists the reservation and barrier together. Existing reservations retain their original manifest and bypass the check for a new peer transaction-trust grant.
- `src/transactions/mutation.rs` applies SQL-only state changes. Admission authority must cover each operation rather than treating peer authentication as resource authorization.
- `docs/authorization.md` keeps ordinary Registry writes operator-only and requires current permissions for workspace/task changes and artifact creation. D2 needs an explicit, narrowly scoped exception to ordinary repeated execution authorization.
- `tests/transaction_protocol.rs` contains fresh-pool/HTTP-server restarts at durable transitions and an actual Worker kill after COMMIT during a peer outage. Those cases do not establish an all-transitions OS-process failure matrix.
- `scripts/cluster_acceptance.py` tests the research fixture through scaling and rolling updates; its reported success does not prove atomic manifest visibility and recovery during those operations.
- `src/api.rs` applies the visibility middleware to ordinary authorization routes, whereas transaction control routes have their own path. Scoped transaction admission and revocation need explicit treatment while a Node is reserved.
- The current peer transaction messages contain the whole manifest, including other Participants' mutation payloads. Peer transaction trust alone is not a subject's permission to disclose all those payloads to every peer.

## Design tree and implementation handoff

The decision frontier is empty after round 3. This means the behavioral choices below are settled, not that the protocol changes or their verification are complete. The user confirmed the final synthesis by requesting implementation.

| Branch                       | Settled decisions                                                                                                                                                          |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Isolation and availability   | D1 Node-wide barrier; D8 operation-boundary visibility; D13 limited control paths; D15 prompt busy rejection and recovery fairness                                         |
| Authority and privacy        | D2 Participant admission boundary; D6 scoped mutation authority; D7 authenticated recovery; D9 current management access; D12 revocation ordering; D14 manifest disclosure |
| Failure and release evidence | D3 retained-state assumption; D4 Node tiers; D10 both distributions, three repetitions and 180-second convergence observation                                              |
| Runtime upgrades             | D5 compatible transaction-aware versions; D11 actual distinct-version evidence and an open gate without a qualifying predecessor                                           |

Implementation should proceed in this dependency order:

1. Define durable admission/authority-attempt and revocation records, immutable identity bindings, the explicit transaction/disclosure action mapping, and a recoverable ordering of remote admission versus revocation. Include abort tombstones and retry recognition in the same design. Verify all generated queries/migrations follow the repository SeaORM/SeaQuery convention.
2. Add narrowly scoped control paths and database guard rules before enabling subject transactions. Prove authority checks and revocation remain usable during a barrier without exposing ordinary data or allowing unrelated writes. Preserve peer authentication and isolate recovery capacity.
3. Connect subject submission, independent mapped admission, disclosure checks, filtered management, exact-ID retries and busy rejection. Retain all mutation/ownership/revision checks and operator-only Registry writes. Update the Dashboard's current-authority and pending-revocation behavior.
4. Add deterministic process/network fault injection and the named case inventory for two, three and sixteen Nodes in Kubernetes and k3s. Keep existing focused protocol regressions as component evidence; establish a real compatible version pair before claiming mixed-version acceptance.
5. Publish the executed evidence register for the exact release candidate and synchronize the transaction, authorization, orchestration and release-status documentation. Keep failed, skipped and unexecuted rows open; close #40 only when every applicable criterion has passing evidence.

The exact schema, endpoint layout, fault-hook implementation, backoff and CI job decomposition are implementation choices within this contract. Admission/revocation ordering is a required proof obligation: the interview does not claim that merely persisting a preflight result solves it. Any implementation finding that changes a settled externally visible boundary must be brought back as a design change, not hidden behind an implementation detail.

## Evidence status

No process, network or cluster acceptance was run in this interview. The accepted decisions do not close any Issue #40 acceptance checkbox. Each future evidence record must identify its exact source revision, runtime image digests, distribution/version, Node/database/replica topology, case ID, repetition, durable fault cut, injected failure, observation trace and expected/actual result. Record fault removal, service restoration and convergence times separately, and record all human interventions. Keep credential values and protected manifest contents out of public reports.

For each case, retain both the continuously observed application behavior and the reconciled durable decisions, mutation revisions, Artifact/event identities and barrier state. A report is incomplete if a required distribution, Node tier, repetition, observation boundary or compatible runtime pair is missing. Document permanent durable-data loss and inconsistent backup restoration as outside the D3 guarantee and link their separate Issue #73 evidence; neither exclusion permits guessing an unresolved transaction's decision.

Issue #40 completion requires all six issue acceptance criteria: durable convergence/visibility/uniqueness, the full fault/retry matrix, subject and peer transaction authority, both cluster distributions and lifecycle operations, pre-admission rejection of unsupported effects, and an honest evidence record. Proposed scenarios, source inspection and existing component tests remain distinct from newly executed release acceptance.
