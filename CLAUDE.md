- Complete authorized work through implementation and verification; decide reversible details independently and ask only when missing information or authorization blocks progress.
- Keep verification proportional to the change; expand it only for new changes, failures, or unresolved concerns.
- Report the outcome, verification evidence, and remaining blockers concisely.
- `main` tracks the stable release; `develop/x.y.z` tracks version `x.y.z` under development.
- Name branches `<semantic-prefix>/issue-<issue-number(s)>-<semantic-name>` (for example, `feat/issue-14-shared-workspace`), using prefixes such as `feat`, `fix`, `hotfix`, or `docs`; join multiple Issue numbers with `and`, and omit the Issue segment when no Issue applies (for example, `docs/worktree-branch-policy`).
- Confirm the authoritative checkout, branch, and existing changes before editing. Preserve unrelated work. Read-only investigation may use the current checkout without creating a branch or worktree.
- Before branching, inspect `git worktree list` and matching names in `git branch -a`. Reuse the task's existing branch and dedicated worktree for continued implementation, review fixes, CI fixes, and conflict resolution. Create a new task branch and dedicated worktree from the intended base only when no suitable task checkout exists or independent work needs isolation. Use the configured `wtp` tool when available, and verify the worktree root, branch, and status before editing.
- Keep each branch focused on one coherent task; related changes across components may stay together when they implement the same behavior. For batch work on multiple independent Issues, follow [Batch Issue Handling](instructions/ISSUE_HANDLING.md); its component, severity, size, and shared-foundation rules apply to that batch workflow.
- Use Rust 2024 conventions and `module.rs` with a sibling `module/` directory instead of `module/mod.rs`.
- Use Reinhardt ORM for application persistence and Reinhardt migrations for schema management. Use Reinhardt Query for supported expressions and schema operations. Raw SQL is allowed only for DDL that the framework cannot express; document each such exception.
- Keep business models and pure rules in `aidash-domain`, use cases and ports in `aidash-application`, process supervision in `aidash-runtime`, external adapters in `aidash-integrations`, and HTTP/persistence adapters plus dependency composition in `server`. Domain and application must not depend on server, Reinhardt, Axum, SQLx, SeaORM, or reqwest.
